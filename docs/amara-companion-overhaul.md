# Amara 伴侣体验与国际化改造方案

> 状态：开发设计稿  
> 日期：2026-10-31  
> 适用范围：记忆可靠性、Dream 梦境记忆、老用户控制台、记忆中心、海外市场与前端信息架构  
> 当前基础：Next.js 14、Supabase、DeepSeek、pgvector、Tailwind CSS

---

## 1. 改造目标

这次改造不是单独增加一个“梦”的功能，也不是只换一套页面皮肤，而是建立完整的产品闭环：

```text
对话 → 可信记忆 → 夜间整理 → Dream 与情绪延续 → 次日交流
  ↑                                               ↓
  └──────── 用户查看、纠正、删除和控制记忆 ────────┘
```

### 1.1 核心目标

1. **记忆可信**：角色记住的内容有来源、能纠正、会失效，不重复、不把 AI 的猜测当成用户事实。
2. **陪伴有连续性**：Dream 承接真实经历与情绪，让角色像有持续生活，而不是每轮重新启动。
3. **能力清晰可见**：用户能看懂 Amara 记住了什么、为什么记得、梦是如何产生的，并能随时修改或删除。
4. **首页各司其职**：营销落地页负责新用户理解与转化；老用户控制台负责情绪价值与日常访问。
5. **支持海外市场**：英文优先、多语言可扩展，支持用户时区、海外支付、隐私与账号数据管理。

### 1.2 非目标

- 不因为新增 Dream 而更换现有 Next.js + Supabase 主架构。
- 不让 Dream 直接写入用户事实库。
- 不在记忆正确性未解决前，单纯依靠更长提示词或更大检索数量掩盖问题。
- 不把老用户控制台做成冰冷的数据分析后台。

## 2. 产品原则

### 2.1 真实与想象分层

- 用户明确说过的话，才能进入用户事实。
- AI 的安慰、猜测、角色扮演和虚构场景，不得反向成为用户事实。
- Dream 可以使用想象，但必须存储在独立类型中。
- 提示词注入时必须区分“真实记忆”“上次状态”“共同经历”“梦境想象”。

### 2.2 记忆必须有生命周期

每条事实至少应具备以下状态之一：

```text
active       当前有效
superseded   已被新事实替代
deleted      用户删除，不再检索
uncertain    存在冲突或证据不足，等待确认
```

“用户以前在上海”可以保留为历史，但“用户现在在上海”在用户搬去杭州后必须失效。

### 2.3 用户拥有最终控制权

- 记忆可查看、修改、删除。
- 删除后不得继续进入提示词。
- 用户可关闭 Dream、主动消息或夜间整理。
- 隐私设置不应藏在不可见的系统提示词中。

### 2.4 情绪价值优先于管理效率

控制台首先回答“Amara 今天和我有什么连接”，其次才回答“我有哪些数据可以管理”。管理功能清晰可见，但不抢占主视觉。

## 3. 目标页面地图

```text
/                       新用户营销落地页
/pricing                价格与方案说明
/login                  登录
/reset-password         找回密码

/app                    老用户日常控制台（需登录）
/chat                   沉浸式聊天
/memories               记忆中心
/dreams                 梦境日历与列表
/dreams/[id]            单篇 Dream 详情
/settings               账号、语言、时区、隐私与通知设置
/settings/privacy       数据导出、记忆清理、账号注销

/terms                  服务条款
/privacy                隐私政策
/content-policy         内容与年龄规则
```

### 3.1 访问逻辑

- 未登录用户访问 `/`：看到落地页。
- 已登录用户访问 `/`：可以查看落地页，但主按钮显示“回到 Amara”，链接到 `/app`。
- 已登录用户完成登录或注册：默认进入 `/app`。
- `/app`、`/chat`、`/memories`、`/dreams` 和 `/settings` 均要求登录。
- 不用强制跳转阻止老用户查看价格、条款等公共页面。

## 4. 页面需求

### 4.1 `/`：新用户落地页

**任务：让新用户理解“为什么这个伴侣值得持续交流”。**

内容顺序：

1. 首屏：一句明确的情绪价值主张 + 开始按钮。
2. 一段短对话示例：展示连续性，而不是通用问答能力。
3. 三步解释：聊天 → 记住 → 夜间消化与次日延续。
4. Dream 示例：明确标为想象，不冒充真实事件。
5. 记忆控制权：用户可查看、纠正和删除。
6. 隐私与年龄边界。
7. 价格与最终行动按钮。

要求：

- 不使用“无所不知”“永远不忘”等无法兑现的宣传。
- 不用通用 AI 工具箱式图标和卖点。
- 英文文案按母语表达重写，不逐字翻译中文。

### 4.2 `/app`：老用户控制台

**首屏核心：继续关系，而不是浏览功能。**

模块顺序：

1. **Amara 此刻**
   - 名字、当前关系阶段、自然的状态描述。
   - 主按钮“继续聊天”。
   - 状态过期后不得显示“正在做某事”。

2. **接着上次**
   - 上次话题或尚未完成的事项。
   - 无内容时不显示空卡片。

3. **昨晚的梦**
   - 最新 Dream 的标题与短摘要。
   - 点击进入详情。
   - 未生成时显示安静的自然状态，不制造失败感。

4. **她最近记住了什么**
   - 最近新增或修正的少量记忆。
   - 提供纠正和进入记忆中心的入口。

5. **我们的足迹**
   - 共同经历、重要时刻和关系里程碑。
   - 不展示单纯为了刺激使用频率的签到或连续天数惩罚。

### 4.3 `/chat`：沉浸式聊天

- 保留当前以对话为中心的界面。
- 减少管理按钮和复杂面板。
- 开场白必须入库，使后续模型能读取。
- 可在回复旁提供轻量入口：“这次用到了 N 条记忆”。
- 展开后可查看记忆内容、来源和纠正入口。
- 用户可以选择“这句话不要记住”。
- 不在聊天气泡中直接暴露向量分数、模型名或调试字段。

### 4.4 `/memories`：记忆中心

建议分组：

- **关于你**：姓名、所在地、工作、稳定身份事实。
- **偏好与习惯**：饮食、作息、喜欢与不喜欢。
- **正在经历**：有明确时效的事项。
- **共同经历**：两人共同完成或经历过的事。
- **历史与已失效**：被纠正的旧事实，默认不参与检索。

每条记忆显示：

- 内容；
- 类型；
- 来源对话的日期或摘要；
- 最近更新时间；
- 当前状态；
- 修改、删除操作。

### 4.5 `/dreams` 与 `/dreams/[id]`

梦境列表采用日期或日历视图，详情包含：

- 标题与正文；
- 当晚情绪主题；
- “由这些真实经历触发”的可折叠来源；
- 明确的想象标识；
- 删除和关闭 Dream 的入口。

Dream 默认不要求用户回复，不制造成瘾式任务压力。

### 4.6 `/settings`

- 显示语言；
- 用户所在时区；
- Dream 开关；
- 主动消息与通知开关；
- 记忆功能开关；
- 隐私、数据导出和账号注销；
- 订阅管理入口。

## 6. 目标记忆架构

### 6.1 记忆类型

| 类型 | 示例 | 默认时效 | 能否成为用户事实 |
|---|---|---|---|
| 稳定事实 `fact` | 用户住在杭州 | 直到被纠正 | 是，需用户消息证据 |
| 偏好 `preference` | 用户不喜欢香菜 | 直到被纠正 | 是，需用户消息证据 |
| 临时事项 `ongoing` | 用户本周准备面试 | 到期、结束或被纠正 | 是，需用户消息证据 |
| 个人经历 `episode` | 用户上次面试很紧张 | 长期保存，可降权 | 是，需用户消息证据 |
| 共同经历 `relationship_event` | 两人第一次互道晚安 | 长期保存 | 需结合双方消息，但不得虚构 |
| 角色状态 `live_state` | Amara 刚散步回来 | 数小时 | 否，只属于 Amara |
| 角色情绪 `emotion_state` | 对话结束时有些不舍 | 随时间衰减 | 否，只属于 Amara |
| 梦境 `dream` | 梦见一起赶车 | 长期作为创作记录 | 否，永远不是用户事实 |

### 6.2 数据表演进

不直接删除现有表，采用兼容迁移：

- `chat_messages`：继续作为原始对话与最终证据来源。
- `user_profiles`：迁移期保留为档案投影；新事实确认后同步生成，避免一次性改坏现有聊天。
- `memory_summaries`：迁移到新的记忆条目结构，迁移完成前保持只读兼容。
- `relationship_events`：继续存共同经历，补充来源证据与状态字段。
- `companions`：继续存人格、关系阶段和即时状态。

### 6.3 新增 `memory_items`

作为用户事实、偏好、临时事项和个人经历的统一来源。

建议字段：

```sql
id                uuid primary key
companion_id      uuid not null references companions(id)
memory_kind       text not null       -- fact / preference / ongoing / episode
memory_key        text                -- residence / job / food.dislike 等
content           text not null       -- 给提示词和界面使用的单一明确表述
status            text not null       -- active / superseded / deleted / uncertain
confidence        numeric not null    -- 0 到 1，不直接等同于模型自报分数
valid_from        timestamptz
valid_to          timestamptz
superseded_by     uuid references memory_items(id)
importance        smallint not null
embedding         vector(1024)
created_at        timestamptz not null
updated_at        timestamptz not null
```

约束：

- 被删除、已替代或已过期的记忆不得进入普通检索。
- `memory_key` 用于识别同一主题的新旧事实，例如 `residence`。
- 每次纠正创建新版本并替代旧版本，不直接消灭全部历史。
- 用户主动删除时，应同时从检索与提示词中移除，而不只是降低权重。

### 6.4 新增 `memory_evidence`

一条记忆可以对应多条证据，一条消息也可支持多条记忆。

```sql
memory_id         uuid references memory_items(id)
message_id        uuid references chat_messages(id)
evidence_type     text not null       -- explicit / correction / context
created_at        timestamptz not null
```

服务端必须验证：

- 消息确实属于当前用户、当前角色和本次处理范围；
- 用户事实至少有对应的用户消息证据；
- 模型返回的消息 ID 不在输入范围内时拒绝写入；
- 不以助手消息单独支持用户事实。

### 6.5 新增 `memory_extraction_state`

```sql
companion_id             uuid primary key
last_message_created_at  timestamptz
last_message_id          uuid
updated_at               timestamptz
```

用途：按 `(created_at, id)` 稳定推进增量游标，避免每轮重复抽取最近 12 条。

抽取任务还应保存运行记录或幂等键，至少保证同一消息区间不会因重试而重复写入。

### 6.6 即时状态与情绪

现有 JSON 中已经有 `updated_at` 的，应真正用于过期判断：

- `live_state`：超过设定时限后只能作为“上次聊天时”的历史，不得写成“正在”。
- `emotion_state`：随时间衰减到人格基线，不允许昨天的情绪永久覆盖今天。
- 状态过期时间初版采用可配置常量，后续依据真实使用数据调整。
- 状态与事实分开检索，不因为语义相似而把旧活动变成长期事实。

## 7. 可信记忆写入流程

### 7.1 每轮即时处理

每轮聊天仍可进行轻量抽取，因为用户的纠正和删除不能等到夜间才生效。

```text
收到本轮消息
→ 校验 session 属于当前用户和当前 companion
→ 保存用户消息与助手回复
→ 获取游标之后的新增消息
→ 模型输出结构化记忆操作
→ 服务端验证证据、字段与操作合法性
→ 新增 / 替代 / 标记不确定 / 不操作
→ 原子推进抽取游标
```

模型输出从“给一份完整档案”改为“给出操作”：

```json
{
  "operations": [
    {
      "action": "add | update | supersede | mark_uncertain | noop",
      "memory_kind": "fact",
      "memory_key": "residence",
      "content": "用户现居杭州",
      "evidence_message_ids": ["消息ID"],
      "valid_from": "可选时间"
    }
  ]
}
```

`confidence` 不应只相信模型自报。服务端根据证据是否明确、是否为用户纠正、是否存在冲突计算或限制其范围。

### 7.2 纠正规则

示例：

```text
旧事实：用户住在上海
新消息：我上个月已经搬去杭州了
```

处理：

1. 新事实以用户消息为证据；
2. 新事实成为 `active`；
3. 旧事实成为 `superseded`，并指向新事实；
4. 后续普通检索只返回新事实；
5. 历史视图仍可以显示“曾住上海”，但不能表述成当前状态。

### 7.3 去重规则

向量相似度只作为辅助，不再单独决定是否重复：

- 相同 `memory_key` 且含义一致：更新或合并证据；
- 相同主题但值冲突：执行替代或标记不确定；
- 不同 `memory_key`：即使语义相似，也不能随意合并；
- embedding 失败时仍可根据来源消息、类型和键做确定性去重；
- 并发写入使用事务、锁或数据库幂等约束，不能只靠“先查再插”。

## 8. 检索与提示词注入

### 8.1 检索顺序

1. 必要的核心信息：用户主动设置的称呼、语言、边界。
2. 当前仍有效且达到相关度门槛的记忆。
3. 当前相关的共同经历。
4. 未过期的角色状态。
5. 最近对话。
6. 可选的 Dream 情绪延续，明确标为想象。

### 8.2 相关度门槛

- 先过滤低相关结果，再执行 Top K。
- 阈值使用固定测试集校准，不凭单次聊天随意调整。
- 短消息不再默认注入 20 条高重要性摘要。
- embedding 不可用时，降级为少量近期、高重要性且仍有效的记忆。
- 召回为空是合法结果，不应为了“看起来有记忆”而强行填充。

### 8.3 可观测性

每次生成建议记录：

```text
recall_query
memory_ids
memory_kind
similarity / final_score
recall_path = semantic / fallback / none
excluded_reason = expired / superseded / below_threshold
prompt_version
```

默认日志不记录完整敏感对话；调试界面仅本人或受控管理员可见。

## 9. Dream 产品与数据设计

### 9.1 生成条件

- 用户开启了 Dream；
- 当前角色当天有足够的新对话或值得延续的情绪事件；
- 同一天同一角色尚未成功生成；
- 记忆整理已完成或达到可用状态；
- 没有内容时允许跳过，不强制每天生成。

初版建议将 Dream 作为会员能力，与现有“长期记忆为会员特权”的产品逻辑一致；该商业规则不得写死在数据层，以便以后调整。

### 9.2 新增 `dream_entries`

```sql
id                  uuid primary key
companion_id        uuid not null references companions(id)
local_date          date not null
timezone            text not null
title               text
content             text not null
emotional_theme     text
next_day_hook       text               -- 次日可选延续，不保证必须使用
source_message_ids  uuid[]
source_memory_ids   uuid[]
source_event_ids    uuid[]
model               text
prompt_version      text
status              text not null      -- draft / published / deleted / failed
generated_at        timestamptz
created_at          timestamptz not null
```

数据库约束：

```text
同一 companion_id + local_date 最多一篇有效 Dream
```

若以后支持 regenerate，应通过版本表或 `version` 字段保留历史，不直接破坏幂等性。

### 9.3 Dream 内容约束

- 可以象征、联想和虚构，但不能伪装成用户真实经历。
- 不生成新的用户姓名、家庭关系、疾病、财务、地址等敏感事实。
- 不利用梦对用户施压，例如“我梦见你离开了，所以你不能走”。
- 不用梦进行 guilt-tripping、控制或制造依赖。
- 不在第二天反复提同一个梦。
- `next_day_hook` 是最多使用一次的可选素材，不是必须执行的指令。

### 9.4 Dream 提示词输入

只允许使用：

- 当天原始对话的受控摘要；
- 当前有效、来源明确的记忆；
- 最近共同经历；
- 当前人格与关系阶段；
- 有明确时效的情绪状态。

不得把上一篇 Dream 当成真实输入。可以引用过去 Dream 做风格连续性，但必须标记为 `past_dream_imagination`。

## 10. 夜间任务流程

### 10.1 调度方式

使用服务端定时入口，例如受密钥保护的 `/api/jobs/nightly`，由部署平台的定时任务调用。

- 调度器按固定周期扫描“到达用户本地夜间时间”的角色；
- 实际生成时间依据用户时区，而不是统一按服务器时间；
- 不用前端保持打开页面来触发；
- 不用客户端时间作为最终幂等依据。

### 10.2 新增 `nightly_jobs`

```sql
id                uuid primary key
companion_id      uuid not null
job_type          text not null       -- consolidate / dream / all
local_date        date not null
status            text not null       -- pending / running / succeeded / failed / skipped
attempts          integer not null
range_start       timestamptz
range_end         timestamptz
last_error        text
started_at        timestamptz
finished_at       timestamptz
created_at        timestamptz not null
```

以 `companion_id + job_type + local_date` 建立幂等约束。

### 10.3 执行顺序

```text
扫描到期角色
→ 创建或锁定 nightly_job
→ 获取本轮原始消息范围
→ 记忆去重、冲突处理、临时事项过期
→ 读取可信记忆与当天经历
→ 生成 Dream
→ 保存 Dream 及来源 ID
→ 生成可选的次日情绪延续
→ 标记任务成功
```

失败规则：

- 记忆整理失败时，不生成基于不完整结果的 Dream；
- Dream 失败不影响原始对话和已有记忆；
- 重试使用同一任务和幂等键，不生成重复文档；
- 达到重试上限后标记失败，记录可诊断错误；
- 不向用户暴露 API 密钥、内部提示词或堆栈。

### 10.4 即时与夜间任务分工

| 能力 | 即时处理 | 夜间处理 |
|---|---|---|
| 用户明确纠正事实 | 是 | 可再次校验 |
| 用户删除记忆 | 是，立即生效 | 无 |
| 新增重要事实 | 是 | 可合并整理 |
| 重复记忆合并 | 基础去重 | 深度整理 |
| 临时状态过期 | 读取时必须判断 | 批量清理 |
| Dream 生成 | 否 | 是 |
| 次日情绪延续 | 读取夜间结果 | 生成候选 |

## 11. API 改造清单

### 现有接口

- `POST /api/companion`
  - 校验会话归属与角色匹配；
  - 保存开场白和正式消息；
  - 使用新的有效记忆检索；
  - 返回本轮使用的记忆 ID 元数据。

- `POST /api/companion/extract`
  - 接收明确的 `session_id` 和消息范围；
  - 增量抽取；
  - 服务端验证证据；
  - 支持事实替代与删除；
  - 具备幂等性。

- `GET /api/companion/memory`
  - 逐步升级为统一记忆列表；
  - 返回来源、状态和类型，而非只有摘要文本。

### 新增接口

```text
GET    /api/app/home              控制台聚合数据
GET    /api/memories              分组查询记忆
PATCH  /api/memories/[id]         修改或确认记忆
DELETE /api/memories/[id]         删除并立即禁止检索
GET    /api/memories/[id]/source  查看来源消息

GET    /api/dreams                梦境列表
GET    /api/dreams/[id]           梦境详情
DELETE /api/dreams/[id]           删除梦境

GET    /api/settings              用户设置
PATCH  /api/settings              更新语言、时区、Dream 和隐私设置

POST   /api/jobs/nightly          内部定时任务，仅密钥或受信调用方可访问
```

所有用户接口继续保持用户与角色归属校验；所有新表启用 RLS。内部定时任务使用受控服务端凭证，不能从浏览器直接调用。

## 12. 海外市场改造

### 12.1 语言与人格

- 英文作为首发语言，中文内容保留在可扩展字典中。
- 初版可使用清晰的文案字典与语言配置，不急于引入复杂路由结构。
- `PERSONA_BLOCKS`、关系阶段、情绪描述、记忆抽取和 Dream 都需要英文版本。
- 英文人格应重新校对口语、边界和亲密程度，不直接逐字翻译。
- 危机求助信息按用户语言和地区提供，不能继续只使用硬编码的国内热线。

建议新增用户设置：

```text
locale              默认 en
timezone            IANA 时区，例如 America/Los_Angeles
dream_enabled
proactive_enabled
memory_enabled
```

### 12.2 时区与日期

- 数据库存储统一使用 `timestamptz`。
- Dream 的 `local_date` 按用户时区计算。
- 问候、隔天判断、关系阶段每日限速和夜间任务统一使用时区工具，不在不同文件里各写一套偏移计算。
- 用户修改时区后，只影响未来调度，不重复补写过去日期的 Dream。

### 12.3 登录与支付

- 保留邮箱登录，评估增加 Google 等海外常用登录方式。
- 新支付建议优先评估 Stripe 订阅；最终选择需结合主体所在地、支持的币种和结算要求。
- 支付宝与海外支付并存期间，订单必须带 `provider`。
- 会员状态由已验证的服务端支付回调更新，客户端支付成功页面不能直接开通会员。
- 支付回调必须幂等，避免重复履约。
- 提供订阅查询、取消、续费状态和支付历史入口。

建议订单或订阅记录至少能区分：

```text
provider
provider_customer_id
provider_subscription_id
provider_event_id
currency
status
current_period_end
```

不要在未验证回调的情况下，用前端返回值覆盖数据库会员状态。

### 12.4 隐私、条款与内容边界

上线前需要完成：

- 英文隐私政策与服务条款；
- 内容政策和年龄要求；
- 记忆查看、删除和数据导出；
- 账号注销及关联数据删除；
- 模型供应商与数据用途说明；
- 支付、退款和订阅取消说明；
- 敏感对话与危机场景的本地化应对。

海外上线仍需遵守目标市场、支付服务商、模型供应商及分发平台的规则，不能把“转向海外”理解为无审核环境。

### 12.5 品牌与落地页

- 保留 Amara 作为角色名时，需明确产品名与角色名的关系。
- 首屏聚焦“被记住、被延续、有共同历史”，而不是抽象地宣传“AI 很强大”。
- 使用可验证的真实产品界面与对话示例。
- 不宣称绝对隐私、永久记忆或治疗能力。

## 13. 分阶段开发计划

## Phase 0：记忆止血与可观测性

**目标：先停止已知的记忆混乱，不引入新数据结构。**

任务：

1. 开场白写入 `chat_messages`，并关联正确会话。
2. `POST /api/companion` 校验 `session_id` 同时属于当前用户和当前角色。
3. 前端将响应头返回的 `sid` 直接传给抽取函数，避免使用旧 React 状态。
4. 同一角色的抽取串行化，失败可见且可重试。
5. 用户消息、助手消息和记忆写入检查数据库错误，不再静默失败。
6. `live_state` 和 `emotion_state` 增加过期判断。
7. 语义检索增加相关度门槛；降级路径减少记忆数量。
8. 增加召回日志，记录记忆 ID、路径、分数和排除原因。

完成标准：

- Amara 下一轮能读取自己的开场白。
- 第一轮抽取不会退回“最近三个会话”的模糊范围。
- 昨天的活动不会在今天被描述为正在发生。
- 无关记忆不会仅因重要性高而被大量注入。

## Phase 1：可信记忆模型与迁移

**目标：解决重复抽取、事实纠正、来源追踪和删除生效。**

任务：

1. 新增 `memory_items`、`memory_evidence`、`memory_extraction_state`。
2. 将抽取输出改为结构化操作，而非完整 JSON 档案覆盖。
3. 实现增量游标和消息区间幂等。
4. 实现事实新增、替代、不确定和删除流程。
5. 迁移现有 `user_profiles` 与 `memory_summaries`，保留原始数据备份。
6. 迁移期使用双读或兼容投影，不直接切断现有聊天。
7. 完成记忆中心后端接口。

完成标准：

- 同一消息重复处理不会产生重复记忆。
- “我搬去杭州了”会使“现在住上海”退出普通检索。
- 删除记忆后，下一轮提示词不再包含该记忆。
- 每条事实能定位到合法的用户来源消息。

## Phase 2：夜间整理与 Dream

**目标：在可信记忆之上增加夜间消化，不制造新的事实污染。**

任务：

1. 新增 `dream_entries`、`nightly_jobs` 和用户 Dream 设置。
2. 实现内部定时入口、用户本地日期计算和任务幂等。
3. 实现夜间去重、冲突检查、临时事项过期。
4. 实现 Dream 生成、来源保存和次日可选延续。
5. Dream 与事实库写入路径完全分离。
6. 增加失败重试、跳过和手动重跑能力。

完成标准：

- 同一角色同一本地日期不会重复生成多篇有效 Dream。
- 无有效对话时可安静跳过。
- Dream 中的想象不会进入 `memory_items`。
- Dream 生成失败不影响正常聊天和记忆。

## Phase 3：控制台、记忆中心与梦境页面

**目标：让用户看见并控制新能力。**

任务：

1. 建立新的应用壳、导航和登录后路由。
2. 开发 `/app` 控制台聚合接口和页面。
3. 开发 `/memories`，支持查看来源、修改和删除。
4. 开发 `/dreams` 列表与详情。
5. 聊天页增加轻量记忆来源与纠正入口。
6. 开发设置页面与隐私入口。
7. 完成移动端导航、空状态、加载状态和错误状态。

完成标准：

- 老用户登录后可直接继续关系，不必经过营销页。
- 用户能找到所有已保存记忆并执行删除。
- 控制台清晰但不过度数据化。
- 移动端主要操作可单手完成，聊天仍保持沉浸。

## Phase 4：英文与海外基础设施

**目标：形成可面向海外新用户测试的完整闭环。**

任务：

1. 建立英文文案字典和英文人格提示词。
2. 用户 locale、timezone 接入问候、关系阶段、Dream 和调度。
3. 新增英文落地页、价格页、隐私政策、条款和内容政策。
4. 接入选定的海外支付和订阅管理。
5. 完成数据导出、记忆清理和账号注销。
6. 检查邮件、支付回跳、错误文案和危机信息的语言一致性。

完成标准：

- 英文用户从落地页到注册、聊天、Dream、记忆管理和付费没有中文断点。
- 夜间任务按用户本地时间运行。
- 支付回调重复发送不会重复履约。
- 注销和删除流程有明确结果，不只隐藏界面数据。

## Phase 5：灰度与质量收敛

1. 使用测试账号进行完整对话回归。
2. 小范围开放 Dream，观察事实污染、重复内容和情绪延续质量。
3. 按真实测试集调整检索门槛，而非只凭主观感觉调权重。
4. 检查控制台是否提升“继续聊天”和记忆纠正的可用性。
5. 逐步扩大英文流量，保留回退开关。

## 14. 必测场景

| 场景 | 预期结果 |
|---|---|
| 开场白说“刚散步回来”，用户接着回应 | 下一轮知道开场白内容，不重新打招呼 |
| 用户第一轮发送消息 | 抽取使用正确的新 session 和消息范围 |
| 同一轮抽取请求重试 | 不生成重复记忆 |
| 用户说“我搬去杭州了” | 旧“现居上海”被替代 |
| 用户删除一条偏好 | 下一轮及夜间任务均不可再使用 |
| 用户只说“嗯，然后呢” | 不注入大量无关摘要 |
| 昨天的情绪是低落，今天重新聊天 | 情绪已衰减，不直接作为此刻状态 |
| 助手曾猜测用户养猫，用户没确认 | 不写为用户事实 |
| Dream 梦见用户养猫 | 不写为用户事实 |
| 同一夜间任务重复执行 | 不重复生成 Dream，不重复整理写入 |
| 用户关闭 Dream | 不再生成，历史处理符合用户设置 |
| 用户跨时区旅行并修改时区 | 不重复补写同一本地日期的 Dream |
| 英文用户触发敏感或危机话题 | 返回适合其语言和地区的安全回应 |
| 支付回调重复送达 | 会员与订单只处理一次 |

## 15. 上线保护与回滚

- 所有新表迁移先备份，再执行。
- 记忆新链路先进行 shadow run：记录新结果但暂不替换旧提示词，比较差异后再切换。
- Dream、记忆中心、英文支付分别使用功能开关。
- 迁移期不删除旧记忆原始数据。
- 出现事实污染时，可关闭新记忆写入而保留聊天；可单独关闭 Dream 而不影响基础记忆。
- 定时任务与支付回调都需要可查询的运行记录和错误记录。
